// a_channel_flow.txt —— a 通道 (放置板物件): FANUC TP 程式的步驟、R[1] 解碼表、時序
//
// a 通道與 b 通道都走 Modbus TCP (ROBOT端設定見 FANUC_工科賽通訊設定 PDF), 訊號定義:
//   DO[1]  顏色請求  ROBOT到達辨識位置後設為 ON, 向樹莓派發出顏色辨識請求
//   DO[2]  顏色確認  樹莓派完成辨識並寫入 R[1] 後設為 ON, 表示顏色資料已準備完成
//   R[1]   顏色代碼  樹莓派回傳的顏色代碼 (預設 red=1, blue=2, green=3)
//   (b 通道用 DO[3] / DO[4] / PR[1], 見 PDF「取得座標 - 訊號交握時序」與 arm_link.py)
//
// 本文件所有數字都來自樹莓派端程式, 改程式就要同步改這裡:
//   顏色 → R[1] 代碼 / 失敗碼 / 保持秒數  → pi_gpio_controller.py 頂端 IO_CODES、FAIL_CODE、HOLD_SEC、FAIL_HOLD_SEC
//   辨識 (投票) 秒數                       → main_contest.py 的 VOTE_SEC
//   起始姿態與電爪開合一次                 → 題目卷「評分規範」(2026 題目卷出來後請再對一次)
//
// a 通道只判斷【顏色】, 不判斷形狀。
// ※ 本檔只描述每一步「要做什麼」; TP 程式的指令語法請以 FANUC 操作手冊為準。
//==============================================================================


//===== R[1] 解碼表 (預設值; 選手若改了 IO_CODES / FAIL_CODE, 這張表要跟著改) =====
//   IO_CODES 裡的 (R2, R3, R4) 三個 0/1 當成二進位, R2 是最高位: R[1] = R2*4 + R3*2 + R4
//
//   IO_CODES 值    R[1]   DO[2]   意義
//   (0, 0, 1)       1      ON     red
//   (0, 1, 0)       2      ON     blue
//   (0, 1, 1)       3      ON     green
//   (1, 1, 1)       7      OFF    【辨識失敗】DO[2] 不會 ON, ROBOT靠 WAIT 逾時後讀 R[1] = 7 得知
//                   0      OFF    待命 / 訊號已收回
//
//   ※ 失敗碼 7 是 IO_CODES 沒用到的數字。新增顏色時不要用 (1, 1, 1)。


//===== 時序 (以ROBOT把 DO[1] 設為 ON 的瞬間為 t = 0) =====
//   樹莓派: t=0 開始投票 VOTE_SEC = 3 秒 (每一幀看到的最大物件顏色投一票)
//   成功: t=3 寫 R[1] = 代碼 → t=4 DO[2] = ON → 保持 HOLD_SEC = 7 秒 → t=11 DO[2] = OFF、R[1] = 0
//   失敗: t=3 寫 R[1] = 7, DO[2] 不 ON → 保持 FAIL_HOLD_SEC = 10 秒 → t=13 R[1] = 0
//
//   TP 等待 DO[2] 的逾時設 8 秒:
//     成功時 t=4 就通過; 失敗時 t=8 逾時, 此時失敗碼還在 (到 t=13), 讀 R[1] = 7 即知失敗。
//   不可設 15 秒: 失敗碼 t=13 已清 0, 逾時後只讀到 0, 分不出「失敗」和「樹莓派沒回應」。


//===== 每一件 a 物件的 TP 步驟 =====
//
//  ┌ 1. 移到題目區 2 的該物件夾取點 (預教點位)
//  ├ 2. 關夾爪; 稍等 (約 0.3 秒) 讓夾爪確實夾住
//  ├ 3. 移到【固定檢測位】
//  │    ※ 此點要讓物件完整入鏡且夠大 (面積要超過該顏色 profile 的 min_area)
//  │    ※ 教這個點位時, 樹莓派同時跑 io_test.py 看畫面, 直到出現綠框、左上角 seen= 顯示正確顏色
//  ├ 4. DO[1] = ON (顏色請求)            → 樹莓派終端印「[a] 收到 ready, 投票 3 秒」
//  ├ 5. WAIT DO[2] = ON, 逾時 8 秒 (理由見上面「時序」)
//  ├ 6. DO[2] = ON 的 7 秒窗內讀 R[1] → 依 1 / 2 / 3 走三個顏色分支
//  ├ 6-1. 逾時的那條分支: 讀 R[1]
//  │    == 7 → 辨識失敗: 建議把物件稍微轉個角度 / 重新對正鏡頭後, 回到第 4 步再試; 或放到暫置區跳過。
//  │    == 0 → 樹莓派沒有回應: 檢查 main_contest.py 是否還在跑、Modbus 連線 (python3 arm_link.py)。
//  ├ 7. 讀光電感測器那路 DI → 深度分支 (題目沒有深度判斷就省略本步; 光電感測器不經樹莓派)
//  ├ 8. DO[1] = OFF (放下顏色請求)
//  │    ※ 不可省略: 樹莓派要看到 DO[1] 回到 OFF (WAIT_RELEASE 狀態) 才會接受下一件的請求
//  │    ※ 下一件要等 DO[2] 已經回到 OFF (t=11 之後) 再設 DO[1] = ON, 否則會讀到上一件的 R[1]
//  ├ 9. 依顏色 (和深度) → 移到題目區 3 對應點位
//  └ 10. 開夾爪, 抬起離開
//
//  → 回到主流程, 接下一件 (下一件是 b 就走 PDF「取得座標 - 訊號交握時序」: DO[3] ON → 等 DO[4] → 用 PR[1] → DO[3] OFF)


//===== 整體 flow 範例 (假設題目要求 5 件: a, b, b, a, b) =====
//
//   Start
//    ├─ 起始姿態 + 電爪開合一次            (題目卷評分規範)
//    ├─ 第 1 件 ── a 子流程 (上面 1~10 步)
//    ├─ 第 2 件 ── b 子流程 (PDF「取得座標 - 訊號交握時序」)
//    ├─ 第 3 件 ── b 子流程
//    ├─ 第 4 件 ── a 子流程
//    ├─ 第 5 件 ── b 子流程
//    └─ 回起始姿態
//
//   b 通道的夾取順序寫在 main_contest.py 的 PICK_ORDER; 用完 PR[1] 會寫成全 0 (X=0, Y=0)。
//   a 與 b 的先後由 TP 程式的排列決定。


//===== 賽前用 io_test.py 驗 a 通道 (樹莓派端, ROBOT不必先寫好 TP) =====
//   python3 io_test.py
//   1~9  送出 IO_CODES 裡第 1~9 個顏色的代碼 (預設 1=red 2=blue 3=green; 不看相機, 純測 Modbus 寫入)
//   f    送出失敗碼 (R[1] = 7, DO[2] 不 ON)
//   0    清掉訊號 (DO[2] OFF、R[1] = 0)
//   r    把相機目前看到的顏色送出去 (和比賽動作一樣)
//   q    離開
//   畫面左上角: seen = 目前看到的顏色, ready = DO[1] 狀態, last IO = 最後送出的顏色
//   對照示教器 DATA → Registers 的 R[1] 與 I/O → Digital Out 的 DO[2]。


//===== 常見問題 =====
//
// Q: 等 DO[2] 一直等不到?
// A: 看樹莓派終端有沒有印「[a] 收到 ready」。
//    沒印 → 樹莓派讀不到 DO[1]: 跑 python3 arm_link.py 檢查連線與 I/O 配置 (io_test.py 左上角 ready= 會即時顯示)。
//    有印但送了失敗碼 → 終端會印「沒看到任何 IO_CODES 裡的顏色」: 物件太小 (min_area)、
//    HSV 沒調好, 或顏色名和 IO_CODES 對不上。
//
// Q: 判到錯的顏色?
// A: 兩個顏色的 HSV 範圍重疊。用 vision_tuner.py 依現場燈光重調 (按 n 切換已存顏色),
//    再用 io_test.py 確認 seen= 顯示正確。
//
// Q: 逾時後讀到 R[1] = 0?
// A: 等待的逾時設太長, 失敗碼已經清掉。改成 8 秒。
